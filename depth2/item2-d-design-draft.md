# Conditional materialization draft (not enabled; after class-c RESULT)

Keep a per-instance arena handle initialized to-1 beside complete scalar field slots. The handle is the materialized-or-not SSA flag: loops/joins use the existing SSA construction; exact alias names share that same handle and fields. The same dominance/closed-identity restrictions reject overlapping dynamic instances. At first escaping pointer use, allocate with the existing alloc helper, check status and return the original failure ABI on growth/error, then write the current fields. Subsequent escaping aliases reuse the handle. No arena layout or transaction/writeback path changes.

After materialization, field reads choose arena slots, and stores choose arena versus scalar according to the flag. A proven noncapturing field clone can still be used: synchronize parameter fields from arena only when materialized, return only changed slots, and write those changes back only when materialized. Capturing or identity-observing calls use the real handle; unknown calls materialize rather than guessing. Failure paths keep all original status checks and private-heap rollback. Object returns require materialization unless a pure fresh-return proof excludes captures inside the producer; materialized identity cannot be copied into a new pure virtual result.

Extend only the same closed generated-IR visitor, using statement-local prefix/suffix lists so materialization occurs on the escaping branch, never hoisted out of that branch. Materialization on a checked failure returns typed dummy values through the existing clone-return builder. A fresh factory whose caller immediately stores the value chooses its original handle call before emission, retaining today's operations on that always-materialized path.

Fail-first cases already recorded in scalar-materialize-cases.py: two aliases appended on only one branch, subsequent alias mutation, error before escape, error after escape (Python replay exactly once), and capacity growth while thousands of list entries share one identity. Tests must require actual scalar/materialized IR, not merely baseline-equivalent output.
