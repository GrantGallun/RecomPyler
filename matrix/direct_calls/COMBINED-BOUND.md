## Choices for the user (sized estimates, no backend change started)

1. **Reuse native Numba support and add managed-object intrinsics beside represented regions (recommended).** About800-1500lines for type/operation adapters, identity-preserving boxes, guards and error ownership, then300-800lines for the first string/bytes/native-method slice. Existing native unicode/bytes/container operations are candidates where strict semantics can be guarded; direct APIs supply opaque boundaries and typed specializations. NRT overhead measured here is a reason to borrow existing references inside a region and own only escaping values, not to allocate MemInfo per operation blindly.
2. **Generate whole-function C extensions.** About1500-3000lines for expression/control-flow emission, ownership/error edges, guards and integration; the C ceiling shows two profitable specializations, while string formatting itself gives no resolved gain. Adds a second emitter and ABI maintenance; avoids requiring NRT MemInfo for every boxed intermediate.
3. **Stay native-kinds-only first.** About600-1200lines for unicode/bytes and cheap recognizer adapters plus strict-domain guards. Direct njit rows identify real reuse, but dynamic objects/callables and C API boundaries remain for a later slice. Generic Numba object mode is feasible JIT-only here, slower on these bodies and unsupported by current AOT export; it is not the preferred production route.

S33.1 and S34.3 reserve the product backend decision for the user. This report supplies the requested concrete evidence; no capability/backend change is accepted until that choice. S32 borrowed string/bytes ceilings may proceed independently. The run remains active and has no DONE checkpoint.
