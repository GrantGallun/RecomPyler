## 1. First-class range values and immutable range capture

**Best next bounded language project.** Exactly 21 saved rows across **seven programs** stop at `range() on int`: base64 (11), unpack_sequence (4), nqueens (2), and generators/hexiom/mdp/comprehensions (1 each). This means a range is used as a value rather than the already supported direct `for ... in range(...)` syntax. The most useful computational entry candidates are [nqueens](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/nqueens/candidate.plan.json), [generators](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/generators/candidate.plan.json), and [hexiom](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/hexiom/candidate.plan.json). Source examples are `cols = range(...)`, recursive tree range slicing, and range/list conditional iterables. [Nqueens source](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_nqueens/run_benchmark.py:46), [tree source](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_generators/run_benchmark.py:29), [hexiom source](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_hexiom/run_benchmark.py:243)

Start with an immutable descriptor and iteration/length, then index/slice support as separately verified operations. Preserve signed start/stop/step, zero-step errors, negative steps, empty ranges, Python index/length overflow and exact integer arithmetic. Large Python integers must decline safely rather than truncate. Capture a range without enumerating it; retain original identity on an unchanged returned input, and audit both loaders/AOT seeds. Unsupported uses or joins must fall back before visible writes.

**Limits:** this does not solve nqueens tuple/generator/set/slice operations, hexiom's range-or-list join/nullable lists/StringIO, mdp's Fraction/defaultdict, or base64's external C routines. Seven affected programs is not seven new native programs. Base64/unpack entries also have little script self time.

## 2. Consume returned iterables inside a larger native region

**Next region-boundary project, building on range values.** There are two concrete tree-consumer source cases: `async for ... in tree(range(...))` and `list(tree(range(...)))`. The former is an observed region decline in [async_generators](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/async_generators/candidate.plan.json): `async for over something other than an async generator`. Its source calls a normal function returning an object whose class supplies `__aiter__`; the current named-generator discovery does not recognize that call result. [Async consumer source](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_async_generators/run_benchmark.py:38)

The synchronous [generators profile](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/generators/candidate.plan.json) supplies the cost counterexample: `Tree.__iter__` is already verified but only 0.030x Python per captured call. Compiling each small tree node is the wrong boundary. Evaluate the iterable-producing expression once, retain its original object/iterator, and reuse existing guarded class/generator dispatch around the complete consumer. This can keep construction and traversal native instead of packing every node at a Python boundary. These are **two confirmed source cases/two programs**; the 20 uncaptured generator-expression rows in six programs are additional investigation leads, not demonstrated gains.

Preserve yield order, return values, aliasing, exceptions, exhaustion, early close, finally blocks and class/MRO rebinding. Compile an async consumer synchronously only when its entire reachable chain cannot actually suspend; otherwise preserve Python scheduling/cancellation. Do not eagerly drain arbitrary generators handed to Python or remove intervening Python effects. The synchronous benchmark also has `perf_counter` boundaries; later hot-loop extraction would need explicit commit/resume boundaries, never whole-entry replay across a completed clock/I/O call. Packing an existing 100000-node graph can still exceed the saved computation, so measure the whole chosen boundary.

## 3. Exact non-machine numeric representations

**Highest-cost representation project; start with evidence, not relaxed arithmetic.** [Pidigits](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/pidigits/candidate.plan.json) has two **observed** large-int entry declines, `extract` and `compose`, contributing 55.3% and 26.8% of that profiled run's self fraction respectively. Those are genuine arbitrary-precision inputs, not ordinary int64 overflow checks to disable. [Pidigits source](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_pidigits/run_benchmark.py:25)

Source inspection identifies two more precision domains across three additional programs: Decimal in [factorial](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_decimal_factorial/run_benchmark.py:23) and [pi](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_decimal_pi/run_benchmark.py:25), and Fraction/defaultdict in [mdp](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_mdp/run_benchmark.py:44). Their saved ordinary-lifter labels are not observed region attempts, so count this as **four source-confirmed programs, only one with directly recorded numeric region rejection**. [Decimal factorial raw](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/decimal_factorial/candidate.plan.json), [Decimal pi raw](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/decimal_pi/candidate.plan.json), [mdp raw](D:/Code/Datathon/recompyler-codex-20261111/wave8-study/results-paired-final/programs/mdp/candidate.plan.json)

A first pilot should preserve exact Python-int operations and ownership, possibly through a guarded boxed/C-API lane; Decimal and Fraction require separate semantics. Preserve reference ownership/lifetimes, errors, floor division, huge shifts, type/subclass dispatch and GIL requirements. Decimal additionally requires live context precision/rounding/traps/flags, and Fraction exact normalization and comparisons. No float substitution, wrapping contract, replay of effectful numeric hooks, or test-trained removal of checks. Existing arithmetic already runs substantially in C; only larger fused control flow may amortize that interface, so speedup is unproven.

## Shared gates and misleading large buckets

Before expanding any subset, expose sample count and capture-failure categories in reports: [snapshot](D:/Code/Datathon/recompyler-codex-20261111/wave10-coverage/src/recompyler/profiler.py:71) currently has a 4096-element budget and no range/frozenset case, while `test_candidate` tries a region only when inputs exist. Meteor's source uses frozensets throughout its hot solver, but its saved “call” message alone cannot identify the first runtime region blocker. Never treat uncaptured data as supported or as proven unsupported syntax.

The 26 “attributes its __init__ does not set” rows span nine programs, mostly standalone partially initialized constructor entries; constructors already work as helpers of larger regions. Compiling tiny constructor wrappers is unlikely to fix boundary costs. Likewise, FastAPI's 87.6%-self `With` row is [server setup with a busy-wait on another thread](D:/Code/Datathon/recompyler-coverage/corpus/pyperformance-1.14.0/benchmarks/bm_fastapi/run_benchmark.py:46), not evidence that compiling context-manager syntax would accelerate HTTP work; GIL/scheduling and external effects matter.

Keep three success gates separate: supported/captured semantics; profitable kernel plus packing; **actual fresh-process selected AOT execution and process gain**. The new [chaos diagnostic plan](D:/Code/Datathon/recompyler-codex-20261111/wave10-coverage-analysis/chaos-profile-diagnostic/plan.json) illustrates why: 2/2 verified native samples and 28.75x per-call speed still produce `worth_running=false` for the unchanged short run, and its legacy-only AOT export needs fresh reuse validation. More syntax cannot by itself remove NumPy/runtime startup or reconstruction costs. Retain the original short case and the separate extended diagnostic; never lower selection thresholds or count forced/tiny-helper native calls as broad Python coverage.
